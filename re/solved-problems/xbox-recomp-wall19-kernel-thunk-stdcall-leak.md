# xbox-recomp-wall19-kernel-thunk-stdcall-leak

**Technique:** Read the runtime's own already-built-in ABI and stack-balance checkers (REX_TRACE mode) instead of hand-tracing; they printed the exact esp delta and which register failed to restore in a single run, pointing straight at the call site

## Notes

Project: og-xbox-recomp-sdk (D:\My apps\og-xbox-recomp-sdk), universal OG Xbox static recompiler, X-Men Legends title. Wall 19: fault at guest 0xE8510069 in a shared COMDAT vtable thunk, stuck at 27,778 guest calls for multiple investigation rounds.

Three earlier rounds (recorded in the project's own ledger, entries #15-#18) chased this as memory corruption inside sub_00209650's dispatch loop - an "aliased registration object" theory, a recursion theory, both eventually refuted by sequence-numbered probing.

Root cause, found in one session: rex_kthunk_fallback (generated by src/writers.c, the recompiler tool itself) dispatches an unimplemented kernel ordinal to a generated weak __imp__ stub. That stub's template is:
  void %s(RecompCtx* c) { rex_unimplemented("%s", 0); c->esp += 4u; }
It only pops its own 4-byte return slot - it has no way to know its own stdcall argbyte count, since the generator emits one generic template for every import regardless of the real function's signature. NtReleaseSemaphore (ordinal 222, 3 stdcall args = 12 bytes) hit this during boot, leaking exactly 12 bytes of guest stack. That hole landed on a completely unrelated function's saved ebx slot several frames up the guest call stack (sub_0020B230, called via sub_00209650's dispatch loop), so its own later `pop ebx` read the corrupted slot instead of its real saved value. ebx was being used as a registration count in the outer sub_00209650 invocation; it came back as a stale aliased address instead of the real small count, and the dispatch loop walked far past the real end of its table into unrelated static data, landing on a shared vtable-slot-0x40 COMDAT thunk called with garbage `this` == the exact fault address.

Found via the runtime's OWN instrumentation (REX_TRACE build), which already existed and just needed to be read carefully: `[ogxbox] STACK: call 0x001EF687 -> sub_00300EE0 esp -12` printed right next to `[ogxbox] ABI: icall 0x0020B230 did not restore ebx (0x00000003 -> 0x011909C0)`. Confirmed with a REX_PROBE (this SDK's own hot-patch-a-generated-.c-file instrument) at the specific function whose internal `call [0x003C6C9C]` resolves at runtime to 0x800000DE = kernel ordinal 0xDE = NtReleaseSemaphore, showing esp short by exactly 12 bytes across that one call.

The bridge dispatch path (a separate, correctly-written code path for kernel calls the SDK DOES implement) already had the fix pattern available: it calls rex_bridge_stdcall_bytes(ordinal) - a real, per-ordinal argbyte table already used correctly there - and adds that many bytes back. The unimplemented-import fallback path just never consulted it.

Fix (src/writers.c, the recompiler itself, universal - benefits every title, not a per-title hook): every generated per-ordinal case in recomp_kthunks.c now wraps its call to the weak __imp__ stub with a top-up against rex_bridge_stdcall_bytes(ordinal) - only raises esp if the stub under-cleaned, never lowers it, so an already-correct override (a hand-written real implementation) is untouched. The fully-unhandled default case (an ordinal not even declared as an import) gets the same treatment instead of a blind +4u.

Gotcha hit while fixing this: editing the recompiler's own C source (src/writers.c) does nothing until the recompiler tool itself (ogxbox.exe) is rebuilt - the SDK's `build()` automation only re-runs the EXISTING compiled tool against title configs, it does not recompile the tool from source. Had to manually rebuild it: the tool's own CMake+ninja build lives at the repo root, and needs the MSVC environment loaded (bare shell can't find clang-cl/kernel32.lib) via vcvars64.bat before ninja will succeed. Only after that did re-running the title's own build(reconfigure=True) pick up the fix.

Result: X-Men Legends guest call count went 27,778 -> 32,272 in one fix, with the sub_00200190/wall-19 fault gone entirely, replaced by a new, different fault - confirming genuine forward progress rather than a fluke. Lesson generalizes to any static recompiler that generates one-size-fits-all stubs for unimplemented imports: if the stub can't know the real callee's calling-convention argbyte count, it must either reject/no-op safely (never touch the stack beyond a fixed, worst-case-safe amount) or consult a real per-symbol signature table if one exists anywhere else in the codebase, rather than trusting a blind constant.
