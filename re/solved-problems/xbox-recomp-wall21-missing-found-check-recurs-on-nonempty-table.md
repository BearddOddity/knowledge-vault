# xbox-recomp-wall21-missing-found-check-recurs-on-nonempty-table

**Technique:** When a fault reports a raw host pointer with no corresponding guest address translation at all, suspect a wildly oversized size/count argument to a real host memcpy/memmove rather than a bad pointer - the pointer can be perfectly valid and still walk off host memory almost instantly if the size argument underflowed to billions of bytes

## Notes

Project: og-xbox-recomp-sdk, X-Men Legends title. An earlier wall (documented separately in this same project's history) had already found and hooked a bug in a string-table remove function: it binary-searches for the name to remove via a separate search function, then unconditionally removes whatever index the search landed on via a memmove - it never checks the search's own found/not-found result. On an empty table the search correctly reports not-found at index 0, and the remove function still "removes index 0", underflowing its count field and computing a gigantic memmove size that walks into unmapped guest memory. The existing fix guarded exactly that one condition: skip the whole remove body when the table's count field is zero.

Wall 21 was the identical defect recurring in a form the count==0 guard did not cover: a non-empty table, where the name being removed was genuinely absent, and the search's not-found return value was the sorted insertion point - which can legitimately equal the table's current count (insert-at-end). (count-1)-index then underflows exactly the same way even with a healthy nonzero count, producing a size close to 4 GB, handed straight to the real host memmove. Because the size was so much larger this time than the smaller empty-table case, the resulting out-of-bounds access walked off HOST memory almost immediately rather than eventually hitting a guest-address-space boundary - producing an access violation whose logged fault line was a bare host pointer with no bracketed guest address at all, a visibly different symptom shape from the earlier occurrence even though the root cause was byte-for-byte the same missing check.

Fix: reimplemented the hook's body to faithfully match the real lifted function line-for-line (verified against the SDK's own faithfulness checker), adding exactly one guard - check the search function's found/not-found flag (returned in AL per that function's own two exit paths, one clearing it, one setting it) immediately after the search call returns, before anything else overwrites that register, and skip straight to the function's own shared tail (which does unrelated, safe cleanup) on not-found. Confirmed the skipped block's own stack pushes for the memmove call and its own cleanup afterward net to zero stack effect, so skipping both together preserves calling-convention balance into the shared tail without needing to hand-adjust anything.

Generalizable lesson: a "we already found this exact bug once" defect is not necessarily fully fixed by a guard scoped to the one triggering condition first observed. A missing return-value check on a search/lookup function is a class of bug, and different callers or different data states can trip the SAME unchecked path through very different, differently-shaped symptoms (a small guest-address-range crash here, a raw host-memory crash there). When re-investigating what looks like a recurrence, check whether the existing fix's guard condition is the FULL fix for the underlying missing-check, or only the specific instance of it that was first observed.
