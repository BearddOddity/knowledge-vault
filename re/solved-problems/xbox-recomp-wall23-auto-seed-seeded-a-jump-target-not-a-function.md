# xbox-recomp-wall23-auto-seed-seeded-a-jump-target-not-a-function

**Technique:** When a crash address has a suspicious repeating byte pattern (0xCCCC-shaped here), check the real binary bytes at the computed base pointer with a disassembler before assuming it is uninitialized data - it may be code, specifically another function's tail plus its inter-function padding. Separately, when a recently auto-seeded function's own body reads a register with no prior assignment anywhere in its lifted C, get that address's real call cross-references before trusting it as an independent function at all

## Notes

Project: og-xbox-recomp-sdk, universal OG Xbox static recompiler, X-Men Legends title. This SDK has an `auto_seed` instrument: it reads unresolved indirect-call-target addresses out of the runtime's own crash log, checks each one decodes as plausible non-degenerate x86 inside the known code range and is not already covered by an existing function, and adds any survivor to the title's function-seed list so the emitter treats it as a real function root next time. It had already correctly caught ~20 genuinely missed functions earlier in the same session (functions reached only through vtable dispatch, invisible to the static scanner - the exact same bug class ReXGlue calls out for X360 recompilation).

Wall 23: after one such auto_seed batch, a new access-violation READ fault appeared at guest address 0xCCCC0014, in a function whose own execution had already been exhaustively probed and proven clean three levels deep (every field read, every downstream function call, all confirmed to complete normally with real, valid-looking values). The obvious-looking theories in order, each investigated and refuted with direct evidence before moving to the next: (1) a garbage pointer sitting in a dynamically-grown array slot (refuted - the array's buffer was a real pool address and the loop walked its full, genuine bound cleanly every time); (2) a metaclass instance ending up with the wrong/generic vtable because its class-specific constructor chain never runs, the same defect family as an earlier wall in this same project (refuted after three full functions in that chain were each individually probed and Ghidra-cross-checked and found to complete without fault).

The actual crash was a DIFFERENT one of the ~17 total calls into the same crash-site function, made from one of the auto_seed-added functions itself, using a code path never before probed. Cross-referencing that auto-seeded function's own address in Ghidra (get_xrefs_to) showed it has ZERO call references - only an unconditional jump and a conditional jump, both from inside a completely different, unrelated function, plus one jump-table data reference also reached only by indirect jump from that same parent. It is a mid-function label / basic block, not a real function entry point at all. It happens to also decode as clean, plausible-looking x86 code when read starting from that address - which is exactly and only what the auto-fixer's plausibility check verifies (decodes cleanly, inside known code range, not degenerate fill bytes, not already covered). It has no way to check for a genuine CALL cross-reference, because that check needs a disassembler with full cross-reference analysis (Ghidra), which the auto-fixer deliberately does not depend on so it can run fast and offline via a bare instruction decoder.

Confirmed mechanically: the auto-seeded function reads a register (ebx) as its very first real instruction with zero prior assignment anywhere in its own lifted body - meaning on real hardware this code never runs as an independent callable routine, it only ever runs via fall-through or a jump table dispatch from inside its true parent function, inheriting whatever register state that parent had already established. Every synthetic call the recompiler's reconstructed call graph now makes to it from elsewhere supplies unrelated, essentially random register/stack state instead. On one specific call path, whatever ended up in a completely unrelated stack slot (confirmed via grep across the whole function body: NEVER written anywhere inside it, purely inherited garbage from the guest stack at that call depth) got read and passed onward as an object pointer into the original crash-site function. That garbage value, read directly from the real Xbox binary at that exact address via Ghidra's byte-level read, was the tail end of a COMPLETELY UNRELATED function's epilogue (add esp; four pops; ret), immediately followed by a long run of 0xCC filler bytes - the standard x86 inter-function code-alignment padding a compiler/linker inserts in gaps between functions. Reading a supposed object field 8 bytes into that padding run landed exactly on the observed crash address, byte for byte.

This retroactively explains where every 0xCCCC-shaped value chased earlier in the same investigation actually came from: compiler code-alignment filler, not uninitialized heap/pool memory and not a missing static constructor, even though both of those theories looked individually plausible and were worth ruling out first given this project's own prior history of exactly those defect classes.

Generalizable lesson for any "seed a missed function from a decode-only plausibility check" auto-fixer (applies well beyond this one SDK): a candidate address decoding as clean, non-degenerate code proves it IS code, not that it is a real, independently-callable function entry point. Code reached only by intra-function jumps or a jump table looks identical to a real function's first instruction under a bare decoder. When Ghidra or an equivalent cross-reference-aware disassembler is available in the same session, cross-check any such candidate's real call references before trusting it for a large or structurally complex function - a genuine function will have at least one CALL xref (or be a documented entry point); one reached only by JMP/jump-table from a single parent is a red flag that it should be coalesced back into that parent's own fragment instead of promoted to an independent seed. This SDK's own fragment-coalescing pass (already used elsewhere to fold split-function fragments back together) is the natural place such a check or fix would eventually belong, though it was not implemented in this session - the fix requires a real design decision (re-coalesce vs. build a register-context-reconstructing wrapper) rather than a quick patch, so it was documented for a fresh continuation rather than guessed at.
