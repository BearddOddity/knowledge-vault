### Wall 19 detail

rex_kthunk_fallback (generated by src/writers.c) dispatched unimplemented kernel imports to a generic weak __imp__ stub that only popped its own 4-byte return slot -- it had no way to know the real stdcall argbyte count for the specific kernel function. NtReleaseSemaphore (3 args, 12 bytes) hit this during boot, leaking 12 bytes of guest stack that landed on an unrelated function's saved ebx, corrupting a registration-table loop count several frames up and eventually crashing through a shared COMDAT vtable thunk with a garbage this. Found via the runtime's own already-built-in ABI and stack-balance checkers (a compile-time trace mode already present in the codebase) -- a stack-imbalance message printed right next to an ABI message naming the exact register that failed to restore. Fixed by topping up esp against the same per-ordinal argbyte table the correctly-written bridge dispatch path already used, for both the per-ordinal case and the fully-unhandled default case in the generator itself -- universal, not a per-title hook.

Gotcha hit: editing the recompiler's own C source does nothing until the recompiler tool itself is rebuilt -- the build automation's plain build() only re-runs the existing compiled tool, never recompiles it from source. Needed a manual ninja rebuild under the MSVC vcvars64 environment before a full reconfigure picked up the fix.

### Wall 21 detail

Same missing-found-check defect as an earlier wall in this project, but on a non-empty table where the searched-for name was genuinely absent and the not-found index equaled the table's own count (insert-at-end) -- (count-1)-index underflowed to roughly 4GB, handed straight to a real memmove as its size. Because the size was so much larger this time, the fault walked off HOST memory directly -- a raw access violation with a bare host pointer and no bracketed guest address at all, a visibly different symptom from the earlier occurrence even though the root cause was identical. Fixed by reimplementing the hook faithfully with one added guard: check the search function's own found flag immediately after the call, before it is clobbered by the next instruction.

## Current wall: 23 -- root cause found, fix not yet applied

One specific auto-seeded function turned out not to be a real function at all. Cross-referencing its address in Ghidra confirmed zero CALL references -- only an unconditional jump and a conditional jump, both from inside a different function, plus one jump-table data reference also reached only by indirect jump from that same parent. It is a mid-function label that happens to also decode as clean, plausible x86 code on its own -- exactly what the missed-function auto-fixer's plausibility check verifies, and exactly the one thing a bare-decoder check cannot distinguish from a real function entry.

Called independently (as the reconstructed call graph now does, from many call sites), it runs with garbage inherited register state -- confirmed via its own first instruction reading a register with zero prior assignment anywhere in its body. On one specific call path this garbage propagated into a completely unwritten stack slot (grepped across the whole function -- zero writes anywhere), which got passed onward as an object pointer. Reading the real binary's bytes at that exact address in Ghidra showed it was the tail of a completely unrelated function's epilogue, immediately followed by a long run of compiler inter-function padding bytes -- reading a field a few bytes in landed exactly on the observed crash address, byte for byte.

This retroactively explains every suspiciously-patterned crash value chased earlier in the investigation: compiler code-alignment padding, not uninitialized heap memory and not a missing static constructor, even though both of those theories looked individually plausible given this project's prior history of exactly those defect classes.

Next session starts here: decide between re-coalescing the mid-function label back into its real parent function's own fragment, or building a narrow hook that reconstructs the correct register context before running the shared logic. Do not guess -- first check how many distinct places in the reconstructed call graph route to this address and whether they share a consistent calling pattern. Full evidence trail lives in this project's own ledger tool, entries in the low-to-mid twenties.

Generalizable finding, also written up separately in this vault under static-recompilation-debugging patterns and as its own solved problem: this is a real, generalizable limitation of the missed-function auto-fixer's plausibility check, not a one-off bug -- it has no way to verify a candidate has a genuine CALL cross-reference without depending on a full disassembler with cross-reference analysis, which would break its fast, offline, decode-only design. Worth a manual cross-check against real cross-references when such a disassembler is available in a session, before trusting an auto-seeded catch for a large or structurally complex function.
