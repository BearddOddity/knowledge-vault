# xbox360-recompiler-gpu-debugging

## Localizing an Xenos "invalid fetch constant" black-screen to a bad guest predicate via shader disassembly

Context: ReXGlue (Xenia-derived Xbox 360 static recompiler) port that boots to a solid black screen with the GPU log spamming `Texture fetch constant (...) has "invalid" type!` every frame, from `TextureCache::BindingInfoFromFetchConstant` (Xenia-lineage code, same in any Xenia-based project: standalone emulator, rexglue, etc).

Don't stop at "the flag exists": `gpu_allow_invalid_fetch_constants=true` silences the warning by skipping the bind, but on a real bug it will NOT fix the picture — verify by actually screenshotting the live window (on Windows: `Get-Process`, get `MainWindowHandle`, `GetWindowRect` via P/Invoke, `Graphics.CopyFromScreen`), don't just trust "no more warnings" as "fixed."

Diagnostic method that worked, cheap and fast:
1. Add temporary log lines (guarded with a comment marking them temporary/removable) at the three natural chokepoints: (a) where the invalid-type case is detected (log the fetch-constant slot index), (b) right before the draw's texture-request call (log vertex+pixel shader ucode hash and the used_texture_mask bitmask), (c) in LoadShader (log guest_address alongside ucode hash, since the hash alone doesn't tell you where in guest memory/address space the shader's microcode lives).
2. Rebuild, run, grep the log for the diagnostic lines — this immediately shows whether it's the SAME shader pair/slot every frame (a real, fixable bug) or scattered across many different draws (more likely a systemic translation issue).
3. Once you have the offending shader's ucode hash, dump its Xenos microcode disassembly. Xenia-lineage renderers usually have a `dump_shaders` cvar/flag (path to write `.ucode.bin`/disassembly files) plus a DXBC-disasm flag. Gotchas: (a) the cvar often only takes `--flag=value`, NOT `--flag value` — silently stays empty with a space and you'll spend time debugging nothing; (b) if there's a persistent shader-storage/pipeline cache keyed by title ID, a cache HIT skips translation (and thus skips the dump) entirely — move/rename the cache directory aside before the run to force fresh translation, then restore it after.
4. Read the disassembly for the specific texture-fetch instruction connected to the reported invalid slot. Xenos ucode wraps whole basic blocks in `cexec <bool_register>` (conditional exec, predicated on a boolean constant) or `(p0)`/`(!p0)` per-instruction predication. If the offending `tfetchND` for that slot sits inside a `cexec bNNN` block, the hardware would only execute it (and thus only care if that texture is bound) when boolean constant bNNN is true. This reframes "invalid fetch constant" from "the GPU/shader-translation code is broken" (it isn't — real conditional branches ARE being translated correctly) to "the CPU-side guest code is setting the wrong boolean constant / not gating this optional texture correctly" — i.e. a recompiled-code correctness bug upstream, not a GPU code bug. This matters for where you spend the next session's time.

General lesson: for "black screen, spam in log" bugs in any GPU-command-stream recompiler/emulator, resist patching the visible symptom (the warning, or blindly toggling compatibility flags) — correlate exact shader identity + fetch slot with its own disassembly before touching anything. The shader disassembly usually tells you in one glance whether the bug is upstream (guest logic) or downstream (translator), which completely changes the fix location.
